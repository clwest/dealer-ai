infrastructure). Every implementation increment cites back
here for scope, invariants, and refinement provenance.

§Milestone 7).** Support recurring background work
generated by earlier milestones — daily floor-plan
interest accrual, aging reports per lifecycle stage,
vendor SLA warnings, photo-derived work (physical-delete

## 0. Engineering practices to preserve from M2–M6

Synthesized from the five prior retrospectives. Every
practice below is a load-bearing constraint on M7.

1. **Increment discipline** (M2/M3/M4/M5/M6 §6 lesson
   1). Each M7 sub-increment ships independently
   verifiable in one session. If a proposed increment
   cannot be described in one sentence with one
   locked invariant, split it.

2. **Backend-first architecture; frontend never owns
   business rules** (M4/M5/M6 §6 lesson 2). M7 may
   ship no frontend at all — scheduled jobs are
   operator-invisible until Milestone 8 dashboards. If
   any operator-facing surface lands, it's a thin
   orchestrator around service verbs.

3. **Provider-neutral boundaries** (M4/M5/M6 §6 lesson
   3). Task queue + scheduler abstracted behind a
   service layer so a future migration between Celery
   / RQ / Dramatiq is possible without touching job
   authors. Broker abstracted similarly (Redis today
   likely; PostgreSQL LISTEN/NOTIFY or SQS
   theoretically substitutable).

4. **Service ownership — one authoritative write path
   per operation** (M4/M5/M6 §6 lesson 4). Every M7
   scheduled job body delegates to a service module
   — the Celery task shell does registration + retry
   + logging; the actual work lives in existing or
   new service modules.

5. **Local vs production parity** (M4/M5/M6 §6 lesson
   5). Development runs Celery + Redis exactly as
   production does. Test suite runs scheduled jobs
   synchronously via `CELERY_TASK_ALWAYS_EAGER=True`
   (or equivalent) so tests never depend on a
   running broker.

6. **Honest verification reporting** (M4/M5/M6 §6
   lesson 6). Job failure surfaces distinctly from
   job success. Silent-swallow of exceptions is
   forbidden. Retry-on-transient-failure explicit;
   escalate-on-repeated-failure explicit.

7. **Storage-first / safer-direction deletion** (M3/M4/
   M5/M6 §6 lesson 7). The M6.2 photo tombstone
   reaper (the first M7 job that actually deletes
   things) MUST verify tombstone-age threshold before
   physical delete. Bytes deleted first, then the
   metadata row — same shape as M3.5.

8. **Load-bearing decisions get user review BEFORE
   code** (M5/M6 §6 lesson 8). Every M7
   `[NEEDS-DECISION-BEFORE-M7.1]` item requires user
   confirmation at the top of SESSION_088 before
   implementation lands.

9. **Distinct domain errors → distinct HTTP status
   codes** (M5/M6 §6 lesson 9). M7 endpoints (if
   any — probably none in v1) inherit this discipline.
   Job-invocation errors surface via structured
   logging + a distinct error class per failure mode.

10. **Read-model properties are pure reads** (M5/M6 §6
    lesson 10). Any new `Vehicle` @property M7 adds
    (unlikely — job schedules are external to the
    read model) must be side-effect-free.

11. **Additive extension over fork** (M6 §6 lesson
    11). Every existing service M7 wraps a scheduled
    job around gets additive extension, not a fork.
    E.g., a `photo_gallery.reap_tombstoned_photos()`
    helper lands in `services/photo_gallery.py`
    alongside the existing verbs.

12. **Zero-planning-amendment sessions are a signal**
    (M6 §6 lesson 12). Aim for clean decisions
    surfaced at planning time so each M7 session
    open confirms recommendations without amendment.

13. **Two-tier customer-visibility gate** (M6 §6
    lesson 13). If any M7 job surfaces
    customer-facing content, apply the M6.5 gate
    split (batch-query = frontline; direct-access =
    frontline + published listing).

### 1.0 The operational questions Milestone 7 must answer

Six questions synthesized from
`INVENTORY_ACQUISITION_MAPPING.md` pain #10 + `RECON_MAPPING.md`
pains #7 + #12 + `BHPH_OPERATIONS_MAPPING.md` pain #2 +
VCP Phase 6. These are the acceptance test for whether
the milestone shipped the right thing.

| # | Question | Research citation |
|---|---|---|
| 1 | **How does floor-plan interest accrue automatically each day?** | INVENTORY §pain #10 (floor plan monitoring manual) |
| 2 | **How does aging-per-stage refresh on a schedule so the operator sees vehicles that have been stuck for N days?** | RECON §pain #7 + §pain #12 (status-chasing) + M6 §7g M8-precursor |
| 3 | **How do vendor SLA warnings fire when a WorkOrder has been in status X longer than Y days?** | RECON §pain #12 (recon ETAs don't match reality) |
| 4 | **How do photo-derived jobs (M6.2 tombstoned-photo physical-delete reaper) run?** | M6 §7g deferred to M7 |

| 6 | **How does the operator (or SRE) see whether a scheduled job ran, when it last ran, and whether it failed?** | Cross-cutting observability requirement |

**Questions Milestone 7 does NOT answer** (deliberate,
per `IMPLEMENTATION_ROADMAP.md` §Milestone 7 scope
boundary):

- Q: *Which vendors finish fastest / cost most?* —
  Milestone 8 (operational intelligence aggregations
  over the data M4 + M7 records).
- Q: *What are the aging-per-stage trends over the last
  6 months?* — Milestone 8. M7 refreshes the raw
  aging snapshots; M8 aggregates them.
- Q: *Can I trigger an ad-hoc report from the UI?* —
  no operator UI for M7 v1; job invocation is
  Celery-Beat-scheduled or shell-invoked.
- Q: *Do async workers autoscale?* — VCP explicitly
  excludes multi-worker autoscaling from M7 v1.

### 1.1 Task queue + scheduler infrastructure

- **Business questions answered.** Precondition for
  Q1-Q6.
- **Citation.** VCP Phase 6 (Celery + Redis named).
- **Shape.** New `backend/dealer_kit/celery.py` module
  wiring the Celery app to Django settings. `broker_url`
  reads from `settings.REDIS_URL` (env-configurable).
  Beat schedule reads from
  `backend/dealer_kit/celery_beat_schedule.py` (a
  dict of task-name → schedule-spec).
- **Test posture.** `CELERY_TASK_ALWAYS_EAGER = True`
  in `settings.py` test-config so tests run scheduled
  jobs synchronously without a running broker.
  Production `CELERY_TASK_ALWAYS_EAGER = False`.
- **Extension seam.** New jobs land in
  `services/<domain>/tasks.py` modules (or
  `services/<domain>.py::tasks` if the service is
  small) so job authors don't touch the Celery app
  wiring.

### 1.2 Floor-plan interest accrual job

- **Business question answered.** Q1.
- **Citation.** INVENTORY §pain #10.
- **Substrate.** M2 ledger (VehicleCost model) +
  `accrue_floor_plan_interest` management command
  (already exists per M2 test suite).
- **Shape.** New `services/floor_plan/tasks.py::accrue_daily_interest`
  Celery task. Calls the existing
  `accrue_floor_plan_interest` service (or moves the
  command's body to a service verb). Scheduled at
  02:00 local dealership time via
  `celery_beat_schedule`.

### 1.3 Aging-per-stage snapshot job

- **Business question answered.** Q2.
- **Citation.** RECON §pain #7 + #12; M6 §7g.
- **Substrate.** M5 lifecycle event log
  (`VehicleStageEvent`).
- **Shape.** New `services/lifecycle_aging/tasks.py::snapshot_stage_ages`
  Celery task. Reads `VehicleStage.entered_at` for
  every current-stage row and writes a snapshot to a
  new model `StageAgingSnapshot` (M7 model —
  `snapshot_at` + `stage` + `count` + `p50_days` +
  `p90_days`). M8 aggregates these snapshots.
- **Alternative:** compute-on-read at M8 endpoint
  time. Trade-off: on-read is simpler but slower for
  large fleets. Load-bearing decision at §5.

### 1.4 Vendor SLA warning job

- **Business question answered.** Q3.
- **Citation.** RECON §pain #12.
- **Substrate.** M4 recon (WorkOrder model — status +
  `estimated_completion_date` + `started_at`).
- **Shape.** New `services/vendor_sla/tasks.py::detect_sla_breaches`
  Celery task. Finds WorkOrders where
  `status='in_progress' AND estimated_completion_date < today`
  OR `status='approved' AND approved_at < today - N days`
  (N per SLA policy). Emits log records at WARNING
  level; Milestone 8 dashboards will consume the log
  aggregation. **No email / SMS / phone-call
  notification in M7 v1** — those channels are
  Milestone 11+ vendor-integration territory.

### 1.5 Photo tombstone reaper job

- **Business question answered.** Q4.
- **Citation.** M6 §7g deferred item.
- **Substrate.** M6.2 `VehiclePhoto` model +
  `services/photo_gallery.py`.
- **Shape.** New `services/photo_gallery.py::reap_tombstoned_photos`
  service verb + `services/photo_gallery/tasks.py::reap_tombstoned_photos_daily`
  Celery task. Deletes storage bytes AND the metadata
  row for `VehiclePhoto` rows where
  `marked_deleted_at < now() - RETENTION_DAYS`.
  Storage-first pattern per M3.5 (delete bytes first;
  retry-on-storage-fault leaves the row intact).
  Retention threshold TBD at §5 (recommend 30 days
  for v1 — long enough for accidental-delete
  recovery, short enough to keep storage costs
  bounded).

### 1.6 BHPH payment reminder cadence job (deferred — no BHPH substrate yet)

- **Business question answered.** Q5.
- **Citation.** BHPH §pain #2.
- **Shape.** Depends on Milestone 12 BHPH module —
  no substrate exists at M7 time. **Defer to
  Milestone 12** and cite this planning doc as the
  intended home when the substrate lands.

### 1.7 Job observability substrate

- **Business question answered.** Q6.
- **Citation.** Cross-cutting.
- **Shape.** Every Celery task decorated with a shared
  `@instrumented_task` decorator that:
  - Logs task-name + args + duration on start / end.
  - Catches + re-raises with structured error logs
    on failure.
  - Increments a Prometheus counter (if
    `django-prometheus` is available) or writes to
    a new `JobRunLog` model (simpler; recommend for
    v1). Load-bearing decision at §5.
- **Retry policy.** Explicit per task. Default: retry
  on transient errors (network, DB deadlock) up to 3
  times with exponential backoff; fail fast on
  programming errors (raise + log).

## 5. Scope discipline + load-bearing decisions

### 5.a `[NEEDS-DECISION-BEFORE-M7.1]` — Broker choice

**Question.** Which message broker?

**Options.**
- **Option A — Redis** (VCP-named default). Simple,
  well-supported, minimal ops overhead. Recommend
  for v1.
- Option B — PostgreSQL LISTEN/NOTIFY. No new
  service to run; reuses the DB. Slower + less
  battle-tested for Celery.
- Option C — RabbitMQ. Overkill for M7 v1's job
  volume.

**Recommended for user review:** **Option A (Redis)**
per VCP mandate.

### 5.b `[NEEDS-DECISION-BEFORE-M7.1]` — Task queue framework

**Question.** Which Python task queue?

**Options.**
- **Option A — Celery** (VCP-named default). Most
  mature; well-integrated with Django;
  `django-celery-beat` provides scheduler.
- Option B — RQ. Simpler API; smaller ecosystem;
  less mature Beat integration.
- Option C — Dramatiq. Newer; simpler retry model;
  smaller community.

**Recommended for user review:** **Option A (Celery)**
per VCP mandate.

### 5.c `[NEEDS-DECISION-BEFORE-M7.1]` — Aging snapshot strategy

**Question.** Compute-on-schedule + persist to
`StageAgingSnapshot` model, or compute-on-read at
M8 endpoint time?

**Options.**
- **Option A — Persist snapshots** (M7.3 ships new
  `StageAgingSnapshot` model + scheduled snapshot
  job). Cheaper reads at M8; costs one new model.
- Option B — Compute-on-read. Simpler M7 scope;
  M8 pays the aggregation cost per request.
- Option C — Both — persist for historical, compute
  latest at read. Larger M7 scope.

**Recommended for user review:** **Option A** —
predictable dashboard latency at M8 justifies the
model + scheduled job.

### 5.d `[NEEDS-DECISION-BEFORE-M7.1]` — Photo retention threshold

**Question.** How long do tombstoned photos survive
before the M7.5 reaper deletes them?

**Options.**
- **Option A — 30 days.** Long enough for accidental-
  delete recovery; short enough to keep storage
  costs bounded.
- Option B — 90 days. More recovery time; higher
  storage cost.
- Option C — Per-dealer configurable via
  `DealerOnboardingProfile.photo_retention_days`.
  Larger M7 scope (schema + onboarding-form
  extension).

**Recommended for user review:** **Option A** — fixed
at 30 for v1; per-dealer configurability deferred
until operator evidence surfaces.

### 5.e `[NEEDS-DECISION-BEFORE-M7.1]` — Job-run observability substrate

**Question.** Where do job-run logs land?

**Options.**
- **Option A — New `JobRunLog` Django model** (simple;
  queryable via Django admin; no new dependency).
- Option B — Prometheus counters via
  `django-prometheus`. Better production
  observability; requires Prometheus in the deploy
  stack.
- Option C — Structured logs to stdout only.
  Simplest; relies on log-aggregation infrastructure
  that doesn't exist yet.

**Recommended for user review:** **Option A** — new
`JobRunLog` model. Fits the dealer-kit deployment
posture (no Prometheus in prod yet). Prometheus
integration can be added later as an additive
decorator wrapping the model write.

### 5.f Test posture

Tests run scheduled jobs synchronously via
`CELERY_TASK_ALWAYS_EAGER = True` gated on
`_is_running_tests()` (per M5.5 signal precedent) so
tests never depend on a running broker. Deferred to
M7.1 implementation.
